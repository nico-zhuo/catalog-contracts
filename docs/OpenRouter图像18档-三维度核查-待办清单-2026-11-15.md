### ① 参考图计费 —— 「是否计费」上游分成三档，本仓策略已对齐，遗留是核对项

  - flux.2 系与 gpt 系：**本仓不暴露参考图 → 零敞口**（D1 决策继续成立；MP/token 浮动计费 `surcharges` 与 perUnit 均撑不起，见 §四 波2-3 说明）。
  - grok / 5-0-pro / 5-5 / NB Pro / NB 2.5-flash：**暴露但未计价**，敞口全部已记 T3 批首账单核对清单（backend 确认 14/19 档有账单注释；`usage.cost` 已写终态 KV，可直接对账）。
- **口径分裂 3 个（本批新发现）**：NB2 / NB2.1 / NB2-lite —— endpoints API 无 input 行（= Images API 通车只收 output），但页面 FAQ 给了 input token 单价（$0.50 / $1.50 / $0.25 每 M）。按用户「以页面为准」口径，**必须在首账单核对时确认 Images API 实收是否含 input token**；若含，NB2/NB2.1 的 14 张参考图最坏 input 成本不再是 0（粗估：$0.50/M × 每图 ~300–1300 tok × 14 张 ≈ $0.002–0.009/单，2–3 积分量级，可被毛利吸收但需记录）。
- **免费 5 个**：klein、flux-3-image、seedream-4.5 / 5-0-flash / 5-0-lite（页面+endpoints 双证）。

### ② Web Search —— 18 个模型在 Images API 通路上**全部无参数、不计费**；3 个 google 模型页面挂出能力+费率属「未来通路」

1. **实拉定论**：18/18 模型 `supported_parameters` 与 `allowed_passthrough_parameters` 均无任何 search/grounding 字段；Images API 文档参数全集亦无。**当前接入路径下 Web Search 不可触发 → 不产生计费。**
2. **3 个 google 模型**（NB2 / NB2.1 / NB Pro）页面明示 **"Web Search at $14.00/1K calls"**（$0.014/次 ≈ 4.2 积分/次 @×300；与旧 Replicate 档 google_search+5 积分几乎同价）。该费率对应 Google native search grounding，在 OpenRouter 上走 **Chat Completions 的 `plugins:[{id:"web"}]` / `:online` 通路**（Google native）；Images API 尚未开放 → 列为**跟踪项**（上游一旦在 Images API 开放 grounding/search 参数即可接入，surcharges 机制现成）。
3. **换源功能回退（需产品知情）**：旧 Replicate nano-banana-2 / 2-1 档有 `google_search` boolean +5 积分（198 个 handler 的先例）；T3 换源 -or 档**未迁移**（model-id-mapping.ts:210-211 注释「OpenRouter 侧无此参数」——上游侧原因，非我方遗漏）。旧档用户可开联网、新档不能。
4. seedream 系 web 联网检索为**内置免费能力**（含在 per-image 价内）；grok / gpt / flux.2 系无 web search。
5. 库内 grounding 先例（清单外）：`flux-3-image-or` 102 档 `grounding:true` passthrough 直传（**免费**，价格含在分辨率档）——BFL flux-3 系专属；klein 无此参数。

### ③ Quality（Low/Medium/High）—— 只有 gpt 系（6 值）与 grok（low/medium）有；grok 已完整暴露，gpt 系锁 high 未暴露

1. **gpt 系 4 档**：上游 `quality: auto|low|medium|high|xhigh|max`。**计费间接但显著**（token 计价，quality 决定输出 token：1024² 下 low $0.0247 / medium $0.0435 / high $0.0527；auto 按 high 计）。本仓 4 档全部锁 `quality:"high"` 显式上送、不暴露（T2 拍板：perUnit(aspect_ratio) 以 quality 恒定为前提）。**若暴露 low/medium/high 可让利用户（low 成本低 53%）但需重构计价**——CreditCostRule 单 paramRef 限制下只能「合并枚举」（grok 先例，8 ratio × 3 quality 组合过多）或「perUnit(quality) 三值、aspect 成本内吸收」。→ **决策点 D1**。
2. **grok-2.0**：上游 `quality: low|medium`（无 high），**直接 variant 计价**。本仓已暴露合并枚举 4 值（low_1k/low_2k/medium_1k/medium_2k）perUnit(quality)，价格与上游完全同构 → **无差距**。
3. **其余 13 档无 quality 参数**（endpoints 实拉；官方文档 "Providers without a quality knob ignore this"）。用户清单中「Quality Low/Medium/High」仅 gpt 系（含 low/medium/high 三值 + xhigh/max 扩展）满足；grok 只有 low/medium。
4. 前端机制（frontend 实证）：quality 枚举渲染**零改动**（QUALITY_NAMES 网格 + CanvasDropdown 兜底），`params.quality.{low,medium,high,xhigh,max,…}` **32 locale 全现成**；若 gpt 系暴露 quality，前端只需 model-id-mapping 注释同步，无代码改动。
