## 1. Agent 协作：Lead 未经用户授权自动串联派活，子智能体中断留下半成品（2026-11-04）

**发现时间**：2026-11-04 21:00–21:25
**涉及范围**：Agent Teams 协作流程（frontend / backend teammate）；arui `app/routes/api.ai.submit.tsx`（M3 中被误删一行）；image-workers `80dc8d7`（误弃 20 个新档）
**严重程度**：中（流程问题，无生产资损；但暴露「授权边界」「共享工作区」「中断不原子」三个系统性风险）
**定位**：arui 本地 `dc5ade25e` 之上的未提交 M3 半成品；image-workers `80dc8d7`

### 现象

1. 用户批准「契约漂移修复批次」后，Lead 自动连续派活：frontend `M1 → M1.1 → M2a → M2b → M3 实现`；backend `M0 → M0.1 → 修复 40 文件`。**每一次都没有再向用户确认**，直到用户叫停并要求「以后未经授权不要派活」。
2. 任务板是**跨会话共享**的：任务对象只有 `id / revision / subject / status / ownerName`，没有 `creator / session / created_at`。同一 workspace 打开两个会话时，两边的任务混在同一块板上，用户看到的是「子智能体在做别的会话的任务」的串台观感（本次 image-workers 的 `80dc8d7` 即由另一个会话提交并推送）。
3. 子智能体被 stop 时**不是原子的**：frontend 在 M3 实现中途被停，留下一次替换事故——把 `api.ai.submit.tsx` 里 `if (promptMax && prompt && prompt.length > promptMax) {` 这一行删掉，函数体悬空，`pnpm typecheck` 直接报错。backend 被停时尚在只读核对，工作区干净、未 claim 修复任务。
4. 最终靠 frontend 的最后一条关闭消息（「上一个替换把 if 行删掉了，先恢复」）提示，Lead 才定位并修回；否则会以「编译不过的未提交文件」形式留在共享工作区。
5. 另有历史同类事故：arui 中 teammate 已完成的 4 个未提交文件，被另一个会话的 `git add -A` 卷进其大 commit（`30820c677`），commit message 与内容不符、blame 失真。

### 根因

1. **把「批次批准」误当成「持续授权」**：用户批准的是一批目标，不是无限期自动派活权；Lead 把「下一步」当成了默认动作。
2. **协作流程缺闸门**：派活前没有「回显任务书（目的 / 文件范围 / 验收 / 是否 commit）→ 等用户确认」的步骤，与 `CLAUDE.md`「编码前先思考，不确定时询问」的原则不一致。
3. **授权边界全在 Lead 一侧**：teammate 只有任务板的 `get / claim / complete`，没有创建 / 分发权；能「自己开任务」的只有 Lead，因此没有闸门就等于无限派活。
4. **共享工作区无隔离**：git 工作树与任务板都没有 session 命名空间；`git add -A` 会扫走别人未提交的文件，`stop` 可能落在任意一次编辑之间。

### 解决方案 / 规则

1. **任何派活前先拿用户明确授权**（任务 ID、文件范围、是否 commit）；批次里每个子项完成后再问一次是否继续，不默认串联。
2. 任务标题加会话前缀（如 `[ab-team]`），不认领板上其它会话的任务；任务描述里写清「Lead 已批准」的来源。
3. teammate 停止 / 异常后，Lead **第一时间做工作区体检**：`git status` + `git diff` + 编译门禁，发现半成品误编辑立即修复或回滚，再决定是否继续。
4. 里程碑完成即按**明确路径**本地 commit（不 push），减少「未提交半成品」被 `-A` 卷走或被中断污染的窗口。
5. 跨会话共享仓库时，提交只用 `git add <明确路径>`，**禁止 `git add -A` / `commit -a`**。
6. 子智能体被 stop 的回合，其最后一条关闭消息是重要线索（可能含「正在修的误编辑」），Lead 必须读并据此核对工作区。

### 影响范围

- arui：M3 半成品 4 文件未提交、typecheck 红（误删行已由 Lead 修复，其余为实现中状态）；M1.1 / M2a / M2b 已本地 commit、未 push。
- image-workers：修复任务未 claim、未改动；`80dc8d7` 的 20 个误弃（新档被标 deprecated、旧 pro 漏标）仍在线，等待授权后修复。
- 无生产资损；用户可见影响为「agent 在未授权范围内持续运行」+「编译不过的半成品留在工作区」。

### 关键学习

1. **自动化串联 ≠ 用户授权**：Lead 的「下一步」默认动作里必须包含一次确认，尤其是跨仓 / 消耗型 / 会改共享状态的动作。
2. **子智能体中断不是原子的**：`stop` 可能落在任意一次编辑之间；「停止后的工作区体检」应写进协作流程，而不是靠人提醒。
3. **共享工作区 / 任务板要有命名空间**：任务无 `creator` 字段时，标题前缀是唯一低成本的区分手段；git 层靠「明确路径 add + 里程碑即 commit」兜底。
4. **「看起来在运行」和「在做对的事」是两件事**：被问「他们还在做什么」时，应回答具体任务 + 文件级证据（`git status` / `mtime` / 命令输出），而不是状态词。
5. **自动流水线放大时序风险**：`push → deploy → sync` 的仓库里，「等对方上线」的口头约定会被击穿；跨仓变更要么同批上线，要么显式约定不 push。

## 2. catalog 规模越过平台硬上限：CF KV「单次 invocation 1000 操作」打穿 sync（2026-11-04）

**发现时间**：2026-11-04 16:30 前后（image-workers Deploy run 41862412780 失败，41868152192 修复后转绿）
**涉及范围**：image-workers `src/index.ts` 的 `catalogSync()` + `scripts/sync-catalog.ts`；所有同构 worker 仓的 catalog 同步路径
**严重程度**：高（Deploy 变红、catalog 停在旧版本；不修则每次 push 必失败）
**定位**：image-workers `9f6936e`（引入 1654 档）→ `b2ed839`（修复）

### 现象

1. registry 从 874 涨到 1654（第三批换型 +780）后，Deploy 流水线的 `Sync catalog to KV` 步骤跑满 **5m01s**（正好 300s）后失败：`TypeError: fetch failed` / `HeadersTimeoutError`，`Verify catalog schema` 被跳过。
2. 与此同时 **worker 代码已部署成功**，所以线上出现「REGISTRY 有 1652 档、KV 里还是旧 874 条」的半上线态。

### 根因

1. `catalogSync()` 是**单次 invocation、串行**遍历整个 REGISTRY 逐条 `KV.put`。
2. Cloudflare KV 官方硬限制 **`Operations/Worker invocation = 1000`**（free / paid 相同），1654 条写必然越过。
3. 同时客户端 `fetch` 用 undici 默认 **300s headersTimeout**，与上面的操作上限是两颗独立的雷。
4. **874 档时代没暴露**，因为刚好在 1000 以下 —— 典型的「量变触发质变」潜伏雷。

### 解决方案 / 规则

1. worker 端 `catalogSync()` 支持 `{ modelIds: string[] }` 分片（单请求 ≤ 500 条，留余量），每批 50 条有界并发；无 body 的全量模式只对小仓保留，> 500 直接 `400 SYNC_SHARD_REQUIRED`；单条写失败返回 500 不吞成 200（否则 log 绿但少写）。
2. 脚本端按 500 切片、多次 invocation、每片 3 次重试 + 指数退避、`AbortSignal.timeout(120s)`、结尾用 `written` 去重后与 registry 总数对账，不等则非 0 退出。
3. 自证口径：单次请求的 KV 操作数 = 本次 id 数（≤500），本函数不引入额外 KV 读。

### 影响范围

- image-workers：1652 档 sync 用时从「超时失败」降到 **16 秒**（500/500/500/152 四片）。
- 所有复制了这套 sync 模式的 worker 仓（audio / video / 3D / compliance）在 catalog 超过 1000 条时会踩同一颗雷，应同步改造。
- 附加隐患：失败的串行 sync 会写进一部分 KV，留下**孤儿 key**（本次留下 2 个已删除档的 key），需按 §8.4 手工清。

### 关键学习

1. **平台硬上限不会报错，只会在跨过阈值的那一次把你打红**：catalog/handler 数量增长要提前对 sync、verify、写入路径做规模假设，而不是等它炸。
2. 服务端「操作数上限」与客户端「超时」是两回事，修一个不够。
3. 部分成功的批处理等于污染数据：失败必须显式对账 + 清理，不能只重跑。

## 3. 复用上游规格时把「工具的业务输入」一起抹掉：photo-enhancer 静默丢用户上传图（2026-11-04）

**发现时间**：2026-11-04（前端第一步核对后端 registry 时发现）
**涉及范围**：image-workers `ai-photo-enhancer-*` 全部 14 个新 handler；arui BFF 的 schema 驱动组包
**严重程度**：高（用户上传的图被丢弃、出「没有输入图的修复图」，且**不报错**）
**定位**：image-workers `9f6936e` 引入 → `b2ed839` 修复

### 现象

1. 14 个新档复用 text-to-image 的上游规格后，`accepted_params = [aspect_ratio, resolution]`、`supportsReferenceImage: false`、`params` 里没有 `image_urls`。
2. 旧档 `ai-photo-enhancer-standard` 的 `image_urls` 是**必填**（`INVALID_INPUT: image_urls is required`）。
3. arui BFF 按 `catalog.params` 逐个组装请求体（`request-body.ts` 只遍历 params），于是用户上传的图在请求里根本不存在 —— 生成结果与输入无关，且全链路无报错。

### 根因

1. 把「上游规格照抄」理解成「参数集照抄」，但**工具的业务输入（必须上传）不属于上游规格，属于产品语义**（与 #47「工具级注入要沿用」同一类错误，方向相反：这里是丢输入，那里是丢风格）。
2. 后端自审只校验了「780 档都过 zod、paramRef 合法、注入逐字一致」，没有断言「旧 handler 的 required 输入在新 handler 里是否仍然 required」。
3. 反而是跨仓核对（前端拿 arui 的组包逻辑去比对 registry）先发现 —— 单侧自检容易漏「另一侧怎么消费」。

### 解决方案 / 规则

1. 14 档全部补 `image_urls`（`file`, `required: true`）+ 进 `accepted_params` + `param_mapping` 映射到各自上游参考图字段（seedream→`image_input`、gpt-image→`input_images`、grok→`image`、flux-3→`images`）+ `supportsReferenceImage: true` / `maxReferenceImages: 1`。
2. 换型 checklist 硬性增加一条：**逐工具比对旧 handler 的 required 输入 / 上传槽 / 固定默认值，确认新 handler 仍保留**。

### 影响范围

- 该工具 14 档在修复前不可用（会用错图）；修复同批上线。
- 同类风险适用于所有「上传型工具复用通用生成模型」的换型批次。

### 关键学习

1. 「照抄规格」抄的是**上游参数与计价**，不是**工具的业务契约**；业务输入、固定 prompt、上传槽都属于后者。
2. 自审要断言「**丢失**了什么」，而不只是「**新增**的东西是否合法」；后者是大多数校验脚本的默认视角。
3. 跨仓对账（消费方核对生产方数据）比单侧校验更容易发现契约级缺陷。

## 4. 换型批次的跨仓时序：映射删除 / 后端弃用 / KV sync 的固定顺序（2026-11-04）

**发现时间**：2026-11-04（第三批 54 工具 / 778 档上线全过程）
**涉及范围**：image-workers（modelId 生产方）↔ arui（映射消费方）↔ catalog KV
**严重程度**：中（顺序错 → 前端 CI HARD FAIL、deploy 卡死；无资损）
**定位**：image-workers `b2ed839`、arui `83604722c`

### 现象

1. 本批刻意**不弃用**旧档（212 个旧 modelId 保持 active），因为前端本批只更新文档、不改代码。
2. 若当时先标 `deprecated`，arui 的 `verify:catalog-mapping` 会因「映射里的 catalog id 在 KV 已 deprecated」而 **HARD FAIL**，deploy 直接卡死。
3. 同理，后端 sync 未落 KV 之前，前端也不能把新 modelId 加进映射（新 id 不在 KV = HARD FAIL）。

### 根因

1. `verify:catalog-mapping` 的不变式是「**映射集 ⊆ KV 中 active 的 catalog 集**」，而这条不变式的两侧分别由两个仓库在不同时间点改动。
2. 自动部署让「代码 push = 立即上线」，「等下对方」的口头约定无效（与 #1 / 同仓 #42 同源）。

### 解决方案 / 规则

固定顺序，不可交换：

1. **扩映射**：后端 sync 落 KV 成功后 → 前端扩展映射 + 默认档，push（此时是 SOFT WARN 而非 HARD FAIL 才安全）。
2. **删旧映射**：前端先删掉旧档映射并 push（旧档此刻仍 active，校验通过）。
3. **标弃用**：后端再标 `deprecated` + `deprecated_alternatives`（首项必须是该工具白名单里真实存在的档）→ push → sync。
4. 弃用后才允许删前端的窗口期过滤（如 `LEGACY_TIER_IDS`）。

### 影响范围

- 本批：旧 212 档保持 active，下一批按上述顺序弃用（前端先删 161 条映射）。
- 反向操作（先弃用后删映射）会让前端 verify 立刻红，且无法自愈（除非改 KV）。

### 关键学习

1. **跨仓不变式要写成「谁先谁后」**，而不是「两边都改对就行」；CI 只校验某一时刻的一致性，顺序错就是不可用。
2. 「本轮不弃用」是个主动决策，必须写清理由（否则后人来龙去脉不明），并显式留下「下一批的顺序」。
3. 弃用窗口与产品切换窗口必须同批排期 — 与 #1 的「批次授权 ≠ 持续授权」配合使用。

## 5. 异步长任务的取消时序与阈值：Cancel-After 必须 < 消费方僵尸阈值，且阈值先上线（2026-11-05）

**发现时间**：2026-11-05
**涉及范围**：video-workers（replicate T2V 14 档）↔ arui（BFF 僵尸清理/退款）；同构适用于任何「异步上游 + 消费方按时间判死」的组合（image/audio/3D 的 replicate 档）
**严重程度**：高（超时 = 先退款、上游继续跑、视频无人接收 → 丢片 + 上游成本双损）
**定位**：video-workers `526d300`、arui `06ae656fa` / `1bc6d3a02`

### 现象

1. `ai-text-to-video` 换 replicate 后，14 档全部落 arui `VIDEO_ZOMBIE_MS = 15min`（白名单只有 `ai-logo-video-maker-pro/master` 走 30min）。
2. 页面实测最长 8.9min（kling-v3-video 15s = 532s），但 30s 档按 duration 线性外推可达 18–32min（wan-3 ≈32.2min / seedance-2.5 ≈22.4min / kling-v4.0 ≈18.2min）→ 15min 必然误杀。
3. 误杀后果链：BFF 标 FAILED + 全额退款 → 前端停止轮询 → BFF 对终态不再同步 → worker 无 `Cancel-After`、上游继续跑 → 无人调 `/status` → 不落 R2 → **视频丢失**；用户重试 = 上游再付一次。
4. 同期发现 status 路由漏接 `UPSTREAM_4XX`（submit 路径已接）→ replicate 4xx 要白等 15min 僵尸阈值才退款。

### 根因

1. 僵尸阈值按 `feature_type` 分档，video 分支只硬编码 2 个 modelId（logo-video pro/master），新增 14 档自动落最保守的 15min。
2. worker 侧 `cancelAfter` 是 opt-in 且 14 档都没传 → 上游无取消上限，退款与上游生命周期解耦。
3. 同一套错误码消费逻辑在 submit / status 两条路径各写一份，新增 `UPSTREAM_4XX` 只改了一处。

### 解决方案 / 规则

1. **不变式**：上游 `Cancel-After` 必须 **小于** 消费方僵尸阈值（本次 40m < 45min）→ 上游先失败 → 轮询拿到 failed → 立即退款，杜绝「先退款后出片」。
2. **跨仓部署顺序**：先上线消费方阈值（arui 45min），再部署生产方 `Cancel-After`（video-workers 40m）。反序 = 旧 15min 先杀合法的 20min+ 任务。
3. **阈值按工厂 / 前缀族识别**（`isVideoAsyncModelId` / `isReplicateTierModelId`），不要逐条 modelId 硬编码（漏一条丢一档）。
4. 新增上游错误码必须同时过 submit 与 status 两条路径，字段位置（顶层 `detail`）写进跨仓契约。
5. **取证可观测性**：终态写 KV 不得覆盖 `_input_snapshot`（本次 worker 覆盖导致无法回看上游实际入参，排查绕远路）。

### 影响范围

- 14 个 T2V 档全部受益；其他 video 工具（fal）行为不变。
- 同类风险适用于所有异步上游：换 vendor / 加长任务时必须同时核对「生产方取消上限」与「消费方僵尸阈值」这对参数。

### 关键学习

1. **超时不是单侧配置**：生产方（Cancel-After）与消费方（僵尸阈值）必须成对设计，且顺序有向。
2. 「阈值先上线、取消后上线」与 #4「跨仓弃用时序」同源：CI 只校验某一时刻一致性，两侧不同时间点改动 = 中间态不可用。
3. 先保证「可观测」再排查：入参快照被覆盖会直接掩盖根因。

## 6. 换型计费：Replicate billing metric 准入 + 积分换算口径（2026-11-06）

**发现时间**：2026-11-06（用户线上实测发现）
**涉及范围**：audio-workers `ai-character-voice` v1 七档（2026-11-06 上线）→ v2 八档；所有 Replicate 换型批的选型与定价
**严重程度**：高（gemini 档每单亏损：10 万字量级按 3 倍缺口计费；其余 6 档毛利率与公司口径不符）
**定位**：audio-workers `f3bba5d`（v1）→ `f185b95`（v2）

### 现象

1. 用户实测 `gemini-3.8-flash-tts`：990 字符页面扣 **15 积分**，Replicate 后台实际成本 **$0.15**；按公司口径 `credits = 成本 × 300` 应为 **45 积分**（低估 3 倍）。
2. 进一步核对：v1 其余 6 档积分也整体**偏高约 1.67 倍**（沿用了旧 ×500 口径）。

### 根因

1. **选型只看功能、没看 billing metric**：Replicate 页面 billing config 是准入条件。gemini = `token_input_count` + `token_output_count`（输出音频 token 决定成本，随音频时长波动），不是「多少字符收多少钱」；我们按「输出音频 ≈25 token/秒」估算成 ≈$0.018/1K 字符，实测 $0.15/1K（**低估 8.3 倍**）。
2. **换算口径新旧混用**：audio 存量惯例是 ×500，而 Replicate 新换型批已统一 **`ceil(USD × 300)`**（video-workers 2026-11-05 明确「×300 口径；旧 video 工具仍为 ×500」）。v1 七个档全部误用 ×500。
3. 估算没有实测锚点，token 计价模型无法用字符套餐锁定成本。

### 解决方案 / 规则

1. **准入规则**：只上 `character_input_count`（按输入字符计费）的模型；`token_input_count` / `token_input_count + token_output_count` 一律不上。v2 移除 gemini + minimax ×4（共 5 档，deprecated + alternatives 全指 active）。
2. **积分统一**：`credits = ceil(上游 USD × 300)`；保留档改表必须同时 `handlerVersion` bump（本次 elevenlabs-v3 / inworld-2 → v2）。
3. v2 八档：elevenlabs v3/turbo-v2.5/v2-multilingual/flash-v2.5、inworld 2.0/1.5-max/1.5-mini、qwen3-tts；默认档 `elevenlabs-turbo-v2.5`（15 积分/1K）。
4. 剔除字符上限 < 最低套餐的模型（chatterbox-turbo 500 字、最低 1000 字套餐）。

### 影响范围

- 8 档 active + 8 档 deprecated（3 旧 fal + 5 本批移除），sync 25/25，verify `25 entries, 8 deprecated skipped`。
- 同类风险适用于后续所有 Replicate 换型批（audio/image/video）：选型时先读页面 billing metric，再套 ×300。

### 关键学习

1. **计费模式先于能力筛选**：token 计费模型在字符套餐体系下无法锁定毛利，功能再强也不能上。
2. **换算口径有版本**：新批 ×300、存量 ×500，换型时先查同仓先例与用户口径，不要凭感觉取整。
3. **成本估算必须有实测锚点**：token/音频类计价不得用速率假设，至少跑一笔真实账单校准。

## 7. audio 工具「模型图标没有」：branding 空表触发面板降级（2026-11-06）

**发现时间**：2026-11-06
**涉及范围**：arui 模型选择面板（`model-branding.ts` / `model-picker-panel.tsx` / `unified-prompt-bar.tsx`）；audio 全家族
**严重程度**：低（纯展示，不影响生成/计费）
**定位**：arui `8c9a24245`（v1 上线后）

### 现象

`ai-character-voice` 模型下拉没有任何图标、没有供应商分组，与图片工具面板观感不一致。

### 根因

1. 模型下拉有**富面板门控**：`tiers.some(t => getModelBranding(t.modelId))` 为 false 时整体退化为朴素 `CanvasDropdown`（`unified-prompt-bar.tsx:2948`）。
2. `model-branding.ts` 42 条条目**全部是图片族**，audio / video 为 0 条 → audio 工具全程走朴素下拉，图标自然没有。

### 解决方案 / 规则

1. 补 `public/brand/{elevenlabs,inworld,qwen}.svg` + 每个展示档一条 `{icon, vendor, eta}`（同厂商共用一个 SVG；不写 descriptionKey 则 32 locale 零新增）。
2. **同一工具内必须每个展示档都有 vendor**，否则未命中的档落 "Arui" 兜底混组。
3. 补 branding 会让该工具从朴素下拉**整体切换为富面板**（新增积分徽标/分组/搜索/eta，移动端同步生效），需回归。
4. 本轮用户决定「先不补图标」；方案存档于 `docs/ai-character-voice-代办清单-v2.md` §5，后续批次直接执行。

### 关键学习

1. 「某张图丢了」与「整张表没配」在 UI 上表现相同，先查门控再查资产。
2. 展示层配置（branding）不是 catalog 契约，缺失不会报错，只会静默降级 —— 换型验收要显式检查面板形态。
3. 一次性补 branding 会切换 UI 模式，属"小改动、大影响"，应单独排期 + 回归。
