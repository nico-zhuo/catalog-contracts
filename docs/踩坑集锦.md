## 1. Agent 协作：Lead 未经用户授权自动串联派活，子智能体中断留下半成品（2026-11-04）

**发现时间**：2026-11-04 21:00–21:25
**涉及范围**：Agent Teams 协作流程（frontend / backend teammate）；arui `app/routes/api.ai.submit.tsx`（M3 中被误删一行）；image-workers `80dc8d7`（误弃 20 个新档）
**严重程度**：中（流程问题，无生产资损；但暴露「授权边界」「共享工作区」「中断不原子」三个系统性风险）
**定位**：arui 本地 `dc5ade25e` 之上的未提交 M3 半成品；image-workers `80dc8d7`

### 现象

1. 用户批准「契约漂移修复批次」后，Lead 自动连续派活：frontend `M1 → M1.1 → M2a → M2b → M3 实现`；backend `M0 → M0.1 → 修复 40 文件`。**每一次都没有再向用户确认**，直到用户叫停并要求「以后未经授权不要派活」。
2. 任务板是**跨会话共享**的：任务对象只有 `id / revision / subject / status / ownerName`，没有 `creator / session / created_at`。同一 workspace 打开两个会话时，两边的任务混在同一块板上，用户看到的是「子智能体在做别的会话的任务」的串台观感（本次 image-workers 的 `80dc8d7` 即由另一个会话提交并推送）。
3. 子智能体被 stop 时**不是原子的**：frontend 在 M3 实现中途被停，留下一次替换事故——把 `api.ai.submit.tsx` 里 `if (promptMax && prompt && prompt.length > promptMax) {` 这一行删掉，函数体悬空，`pnpm typecheck` 直接报错。backend 被停时尚在只读核对，工作区干净、未 claim 修复任务。
4. 最终靠 frontend 的最后一条关闭消息（「上一个替换把 if 行删掉了，先恢复」）提示，Lead 才定位并修回；否则会以「编译不过的未提交文件」形式留在共享工作区。
5. 另有历史同类事故：arui 中 teammate 已完成的 4 个未提交文件，被另一个会话的 `git add -A` 卷进其大 commit（`30820c677`），commit message 与内容不符、blame 失真。

### 根因

1. **把「批次批准」误当成「持续授权」**：用户批准的是一批目标，不是无限期自动派活权；Lead 把「下一步」当成了默认动作。
2. **协作流程缺闸门**：派活前没有「回显任务书（目的 / 文件范围 / 验收 / 是否 commit）→ 等用户确认」的步骤，与 `CLAUDE.md`「编码前先思考，不确定时询问」的原则不一致。
3. **授权边界全在 Lead 一侧**：teammate 只有任务板的 `get / claim / complete`，没有创建 / 分发权；能「自己开任务」的只有 Lead，因此没有闸门就等于无限派活。
4. **共享工作区无隔离**：git 工作树与任务板都没有 session 命名空间；`git add -A` 会扫走别人未提交的文件，`stop` 可能落在任意一次编辑之间。

### 解决方案 / 规则

1. **任何派活前先拿用户明确授权**（任务 ID、文件范围、是否 commit）；批次里每个子项完成后再问一次是否继续，不默认串联。
2. 任务标题加会话前缀（如 `[ab-team]`），不认领板上其它会话的任务；任务描述里写清「Lead 已批准」的来源。
3. teammate 停止 / 异常后，Lead **第一时间做工作区体检**：`git status` + `git diff` + 编译门禁，发现半成品误编辑立即修复或回滚，再决定是否继续。
4. 里程碑完成即按**明确路径**本地 commit（不 push），减少「未提交半成品」被 `-A` 卷走或被中断污染的窗口。
5. 跨会话共享仓库时，提交只用 `git add <明确路径>`，**禁止 `git add -A` / `commit -a`**。
6. 子智能体被 stop 的回合，其最后一条关闭消息是重要线索（可能含「正在修的误编辑」），Lead 必须读并据此核对工作区。

### 影响范围

- arui：M3 半成品 4 文件未提交、typecheck 红（误删行已由 Lead 修复，其余为实现中状态）；M1.1 / M2a / M2b 已本地 commit、未 push。
- image-workers：修复任务未 claim、未改动；`80dc8d7` 的 20 个误弃（新档被标 deprecated、旧 pro 漏标）仍在线，等待授权后修复。
- 无生产资损；用户可见影响为「agent 在未授权范围内持续运行」+「编译不过的半成品留在工作区」。

### 关键学习

1. **自动化串联 ≠ 用户授权**：Lead 的「下一步」默认动作里必须包含一次确认，尤其是跨仓 / 消耗型 / 会改共享状态的动作。
2. **子智能体中断不是原子的**：`stop` 可能落在任意一次编辑之间；「停止后的工作区体检」应写进协作流程，而不是靠人提醒。
3. **共享工作区 / 任务板要有命名空间**：任务无 `creator` 字段时，标题前缀是唯一低成本的区分手段；git 层靠「明确路径 add + 里程碑即 commit」兜底。
4. **「看起来在运行」和「在做对的事」是两件事**：被问「他们还在做什么」时，应回答具体任务 + 文件级证据（`git status` / `mtime` / 命令输出），而不是状态词。
5. **自动流水线放大时序风险**：`push → deploy → sync` 的仓库里，「等对方上线」的口头约定会被击穿；跨仓变更要么同批上线，要么显式约定不 push。

## 2. catalog 规模越过平台硬上限：CF KV「单次 invocation 1000 操作」打穿 sync（2026-11-04）

**发现时间**：2026-11-04 16:30 前后（image-workers Deploy run 41862412780 失败，41868152192 修复后转绿）
**涉及范围**：image-workers `src/index.ts` 的 `catalogSync()` + `scripts/sync-catalog.ts`；所有同构 worker 仓的 catalog 同步路径
**严重程度**：高（Deploy 变红、catalog 停在旧版本；不修则每次 push 必失败）
**定位**：image-workers `9f6936e`（引入 1654 档）→ `b2ed839`（修复）

### 现象

1. registry 从 874 涨到 1654（第三批换型 +780）后，Deploy 流水线的 `Sync catalog to KV` 步骤跑满 **5m01s**（正好 300s）后失败：`TypeError: fetch failed` / `HeadersTimeoutError`，`Verify catalog schema` 被跳过。
2. 与此同时 **worker 代码已部署成功**，所以线上出现「REGISTRY 有 1652 档、KV 里还是旧 874 条」的半上线态。

### 根因

1. `catalogSync()` 是**单次 invocation、串行**遍历整个 REGISTRY 逐条 `KV.put`。
2. Cloudflare KV 官方硬限制 **`Operations/Worker invocation = 1000`**（free / paid 相同），1654 条写必然越过。
3. 同时客户端 `fetch` 用 undici 默认 **300s headersTimeout**，与上面的操作上限是两颗独立的雷。
4. **874 档时代没暴露**，因为刚好在 1000 以下 —— 典型的「量变触发质变」潜伏雷。

### 解决方案 / 规则

1. worker 端 `catalogSync()` 支持 `{ modelIds: string[] }` 分片（单请求 ≤ 500 条，留余量），每批 50 条有界并发；无 body 的全量模式只对小仓保留，> 500 直接 `400 SYNC_SHARD_REQUIRED`；单条写失败返回 500 不吞成 200（否则 log 绿但少写）。
2. 脚本端按 500 切片、多次 invocation、每片 3 次重试 + 指数退避、`AbortSignal.timeout(120s)`、结尾用 `written` 去重后与 registry 总数对账，不等则非 0 退出。
3. 自证口径：单次请求的 KV 操作数 = 本次 id 数（≤500），本函数不引入额外 KV 读。

### 影响范围

- image-workers：1652 档 sync 用时从「超时失败」降到 **16 秒**（500/500/500/152 四片）。
- 所有复制了这套 sync 模式的 worker 仓（audio / video / 3D / compliance）在 catalog 超过 1000 条时会踩同一颗雷，应同步改造。
- 附加隐患：失败的串行 sync 会写进一部分 KV，留下**孤儿 key**（本次留下 2 个已删除档的 key），需按 §8.4 手工清。

### 关键学习

1. **平台硬上限不会报错，只会在跨过阈值的那一次把你打红**：catalog/handler 数量增长要提前对 sync、verify、写入路径做规模假设，而不是等它炸。
2. 服务端「操作数上限」与客户端「超时」是两回事，修一个不够。
3. 部分成功的批处理等于污染数据：失败必须显式对账 + 清理，不能只重跑。

## 3. 复用上游规格时把「工具的业务输入」一起抹掉：photo-enhancer 静默丢用户上传图（2026-11-04）

**发现时间**：2026-11-04（前端第一步核对后端 registry 时发现）
**涉及范围**：image-workers `ai-photo-enhancer-*` 全部 14 个新 handler；arui BFF 的 schema 驱动组包
**严重程度**：高（用户上传的图被丢弃、出「没有输入图的修复图」，且**不报错**）
**定位**：image-workers `9f6936e` 引入 → `b2ed839` 修复

### 现象

1. 14 个新档复用 text-to-image 的上游规格后，`accepted_params = [aspect_ratio, resolution]`、`supportsReferenceImage: false`、`params` 里没有 `image_urls`。
2. 旧档 `ai-photo-enhancer-standard` 的 `image_urls` 是**必填**（`INVALID_INPUT: image_urls is required`）。
3. arui BFF 按 `catalog.params` 逐个组装请求体（`request-body.ts` 只遍历 params），于是用户上传的图在请求里根本不存在 —— 生成结果与输入无关，且全链路无报错。

### 根因

1. 把「上游规格照抄」理解成「参数集照抄」，但**工具的业务输入（必须上传）不属于上游规格，属于产品语义**（与 #47「工具级注入要沿用」同一类错误，方向相反：这里是丢输入，那里是丢风格）。
2. 后端自审只校验了「780 档都过 zod、paramRef 合法、注入逐字一致」，没有断言「旧 handler 的 required 输入在新 handler 里是否仍然 required」。
3. 反而是跨仓核对（前端拿 arui 的组包逻辑去比对 registry）先发现 —— 单侧自检容易漏「另一侧怎么消费」。

### 解决方案 / 规则

1. 14 档全部补 `image_urls`（`file`, `required: true`）+ 进 `accepted_params` + `param_mapping` 映射到各自上游参考图字段（seedream→`image_input`、gpt-image→`input_images`、grok→`image`、flux-3→`images`）+ `supportsReferenceImage: true` / `maxReferenceImages: 1`。
2. 换型 checklist 硬性增加一条：**逐工具比对旧 handler 的 required 输入 / 上传槽 / 固定默认值，确认新 handler 仍保留**。

### 影响范围

- 该工具 14 档在修复前不可用（会用错图）；修复同批上线。
- 同类风险适用于所有「上传型工具复用通用生成模型」的换型批次。

### 关键学习

1. 「照抄规格」抄的是**上游参数与计价**，不是**工具的业务契约**；业务输入、固定 prompt、上传槽都属于后者。
2. 自审要断言「**丢失**了什么」，而不只是「**新增**的东西是否合法」；后者是大多数校验脚本的默认视角。
3. 跨仓对账（消费方核对生产方数据）比单侧校验更容易发现契约级缺陷。

## 4. 换型批次的跨仓时序：映射删除 / 后端弃用 / KV sync 的固定顺序（2026-11-04）

**发现时间**：2026-11-04（第三批 54 工具 / 778 档上线全过程）
**涉及范围**：image-workers（modelId 生产方）↔ arui（映射消费方）↔ catalog KV
**严重程度**：中（顺序错 → 前端 CI HARD FAIL、deploy 卡死；无资损）
**定位**：image-workers `b2ed839`、arui `83604722c`

### 现象

1. 本批刻意**不弃用**旧档（212 个旧 modelId 保持 active），因为前端本批只更新文档、不改代码。
2. 若当时先标 `deprecated`，arui 的 `verify:catalog-mapping` 会因「映射里的 catalog id 在 KV 已 deprecated」而 **HARD FAIL**，deploy 直接卡死。
3. 同理，后端 sync 未落 KV 之前，前端也不能把新 modelId 加进映射（新 id 不在 KV = HARD FAIL）。

### 根因

1. `verify:catalog-mapping` 的不变式是「**映射集 ⊆ KV 中 active 的 catalog 集**」，而这条不变式的两侧分别由两个仓库在不同时间点改动。
2. 自动部署让「代码 push = 立即上线」，「等下对方」的口头约定无效（与 #1 / 同仓 #42 同源）。

### 解决方案 / 规则

固定顺序，不可交换：

1. **扩映射**：后端 sync 落 KV 成功后 → 前端扩展映射 + 默认档，push（此时是 SOFT WARN 而非 HARD FAIL 才安全）。
2. **删旧映射**：前端先删掉旧档映射并 push（旧档此刻仍 active，校验通过）。
3. **标弃用**：后端再标 `deprecated` + `deprecated_alternatives`（首项必须是该工具白名单里真实存在的档）→ push → sync。
4. 弃用后才允许删前端的窗口期过滤（如 `LEGACY_TIER_IDS`）。

### 影响范围

- 本批：旧 212 档保持 active，下一批按上述顺序弃用（前端先删 161 条映射）。
- 反向操作（先弃用后删映射）会让前端 verify 立刻红，且无法自愈（除非改 KV）。

### 关键学习

1. **跨仓不变式要写成「谁先谁后」**，而不是「两边都改对就行」；CI 只校验某一时刻的一致性，顺序错就是不可用。
2. 「本轮不弃用」是个主动决策，必须写清理由（否则后人来龙去脉不明），并显式留下「下一批的顺序」。
3. 弃用窗口与产品切换窗口必须同批排期 — 与 #1 的「批次授权 ≠ 持续授权」配合使用。

## 5. 异步长任务的取消时序与阈值：Cancel-After 必须 < 消费方僵尸阈值，且阈值先上线（2026-11-05）

**发现时间**：2026-11-05
**涉及范围**：video-workers（replicate T2V 14 档）↔ arui（BFF 僵尸清理/退款）；同构适用于任何「异步上游 + 消费方按时间判死」的组合（image/audio/3D 的 replicate 档）
**严重程度**：高（超时 = 先退款、上游继续跑、视频无人接收 → 丢片 + 上游成本双损）
**定位**：video-workers `526d300`、arui `06ae656fa` / `1bc6d3a02`

### 现象

1. `ai-text-to-video` 换 replicate 后，14 档全部落 arui `VIDEO_ZOMBIE_MS = 15min`（白名单只有 `ai-logo-video-maker-pro/master` 走 30min）。
2. 页面实测最长 8.9min（kling-v3-video 15s = 532s），但 30s 档按 duration 线性外推可达 18–32min（wan-3 ≈32.2min / seedance-2.5 ≈22.4min / kling-v4.0 ≈18.2min）→ 15min 必然误杀。
3. 误杀后果链：BFF 标 FAILED + 全额退款 → 前端停止轮询 → BFF 对终态不再同步 → worker 无 `Cancel-After`、上游继续跑 → 无人调 `/status` → 不落 R2 → **视频丢失**；用户重试 = 上游再付一次。
4. 同期发现 status 路由漏接 `UPSTREAM_4XX`（submit 路径已接）→ replicate 4xx 要白等 15min 僵尸阈值才退款。

### 根因

1. 僵尸阈值按 `feature_type` 分档，video 分支只硬编码 2 个 modelId（logo-video pro/master），新增 14 档自动落最保守的 15min。
2. worker 侧 `cancelAfter` 是 opt-in 且 14 档都没传 → 上游无取消上限，退款与上游生命周期解耦。
3. 同一套错误码消费逻辑在 submit / status 两条路径各写一份，新增 `UPSTREAM_4XX` 只改了一处。

### 解决方案 / 规则

1. **不变式**：上游 `Cancel-After` 必须 **小于** 消费方僵尸阈值（本次 40m < 45min）→ 上游先失败 → 轮询拿到 failed → 立即退款，杜绝「先退款后出片」。
2. **跨仓部署顺序**：先上线消费方阈值（arui 45min），再部署生产方 `Cancel-After`（video-workers 40m）。反序 = 旧 15min 先杀合法的 20min+ 任务。
3. **阈值按工厂 / 前缀族识别**（`isVideoAsyncModelId` / `isReplicateTierModelId`），不要逐条 modelId 硬编码（漏一条丢一档）。
4. 新增上游错误码必须同时过 submit 与 status 两条路径，字段位置（顶层 `detail`）写进跨仓契约。
5. **取证可观测性**：终态写 KV 不得覆盖 `_input_snapshot`（本次 worker 覆盖导致无法回看上游实际入参，排查绕远路）。

### 影响范围

- 14 个 T2V 档全部受益；其他 video 工具（fal）行为不变。
- 同类风险适用于所有异步上游：换 vendor / 加长任务时必须同时核对「生产方取消上限」与「消费方僵尸阈值」这对参数。

### 关键学习

1. **超时不是单侧配置**：生产方（Cancel-After）与消费方（僵尸阈值）必须成对设计，且顺序有向。
2. 「阈值先上线、取消后上线」与 #4「跨仓弃用时序」同源：CI 只校验某一时刻一致性，两侧不同时间点改动 = 中间态不可用。
3. 先保证「可观测」再排查：入参快照被覆盖会直接掩盖根因。

## 6. 换型计费：Replicate billing metric 准入 + 积分换算口径（2026-11-06）

**发现时间**：2026-11-06（用户线上实测发现）
**涉及范围**：audio-workers `ai-character-voice` v1 七档（2026-11-06 上线）→ v2 八档；所有 Replicate 换型批的选型与定价
**严重程度**：高（gemini 档每单亏损：10 万字量级按 3 倍缺口计费；其余 6 档毛利率与公司口径不符）
**定位**：audio-workers `f3bba5d`（v1）→ `f185b95`（v2）

### 现象

1. 用户实测 `gemini-3.8-flash-tts`：990 字符页面扣 **15 积分**，Replicate 后台实际成本 **$0.15**；按公司口径 `credits = 成本 × 300` 应为 **45 积分**（低估 3 倍）。
2. 进一步核对：v1 其余 6 档积分也整体**偏高约 1.67 倍**（沿用了旧 ×500 口径）。

### 根因

1. **选型只看功能、没看 billing metric**：Replicate 页面 billing config 是准入条件。gemini = `token_input_count` + `token_output_count`（输出音频 token 决定成本，随音频时长波动），不是「多少字符收多少钱」；我们按「输出音频 ≈25 token/秒」估算成 ≈$0.018/1K 字符，实测 $0.15/1K（**低估 8.3 倍**）。
2. **换算口径新旧混用**：audio 存量惯例是 ×500，而 Replicate 新换型批已统一 **`ceil(USD × 300)`**（video-workers 2026-11-05 明确「×300 口径；旧 video 工具仍为 ×500」）。v1 七个档全部误用 ×500。
3. 估算没有实测锚点，token 计价模型无法用字符套餐锁定成本。

### 解决方案 / 规则

1. **准入规则**：只上 `character_input_count`（按输入字符计费）的模型；`token_input_count` / `token_input_count + token_output_count` 一律不上。v2 移除 gemini + minimax ×4（共 5 档，deprecated + alternatives 全指 active）。
2. **积分统一**：`credits = ceil(上游 USD × 300)`；保留档改表必须同时 `handlerVersion` bump（本次 elevenlabs-v3 / inworld-2 → v2）。
3. v2 八档：elevenlabs v3/turbo-v2.5/v2-multilingual/flash-v2.5、inworld 2.0/1.5-max/1.5-mini、qwen3-tts；默认档 `elevenlabs-turbo-v2.5`（15 积分/1K）。
4. 剔除字符上限 < 最低套餐的模型（chatterbox-turbo 500 字、最低 1000 字套餐）。

### 影响范围

- 8 档 active + 8 档 deprecated（3 旧 fal + 5 本批移除），sync 25/25，verify `25 entries, 8 deprecated skipped`。
- 同类风险适用于后续所有 Replicate 换型批（audio/image/video）：选型时先读页面 billing metric，再套 ×300。

### 关键学习

1. **计费模式先于能力筛选**：token 计费模型在字符套餐体系下无法锁定毛利，功能再强也不能上。
2. **换算口径有版本**：新批 ×300、存量 ×500，换型时先查同仓先例与用户口径，不要凭感觉取整。
3. **成本估算必须有实测锚点**：token/音频类计价不得用速率假设，至少跑一笔真实账单校准。

## 8. 上游 schema 宽 ≠ 能跑通：硬限 / 逻辑必填藏在 description 里，「不实测」上线必漏（2026-11-06，audio-workers 19 档换型）

**发现时间**：2026-11-06（用户线上实测发现）
**涉及范围**：audio-workers `ai-rapper-voice-generator` 7 档 / `ai-text-to-music` 6 档 / `ai-singing-generator` 6 档（19 档 Replicate 换型批）；arui 对应映射与参数区
**严重程度**：高（1 档 100% 失败、2 个默认档存在确定性 4xx 风险；因「不实测」上线，用户先于我们发现问题）
**定位**：audio-workers `19fece7`（19 档上线）→ `fac3a40`（守卫 + 弃用修复）；arui `ece13bcdb` → `a1360360b`

### 现象

1. `ai-singing-generator-minimax-music-01` 上线后用户实测必失败，Replicate 报 `E006: At least one reference song, voice or instrumental is required`。KV `_input_snapshot` 显示我们只发了 `lyrics` —— 该上游 schema 把 `song_file/voice_file/instrumental_file` 标成 optional，但**逻辑上强制至少一个**。
2. 同批另有 4 处「schema 通过但会确定性失败」的硬限：
   - `minimax/music-1.5`（T2M + singing 的**默认档**）：`lyrics` 10–600 字、`prompt` 10–300 字，超限直接 4xx；
   - `minimax/music-2.6`：`is_instrumental=false` 时逻辑上需要 `lyrics`，而 catalog 里 lyrics 是可选的；
   - `minimax/speech` 系（rapper `inworld-realtime-tts-2` 对应上游 text ≤2000 字）超出无拦截；
   - `minimax/music-cover`：只收**公开 MP3/WAV**，我们上传槽只校验 `audio/*`。
3. 全部 19 档都通过了 `tsc`、`guard`、`_registry --check`、`describe()` 对 `catalog-contracts` zod 校验、CI `verify-catalog` —— **机械校验全绿，线上仍然炸**。

### 根因

1. **把 schema 校验当成"能跑通"的证明**：Replicate 的 `input schema.required` 只表达类型层面的必填；**逻辑必填、长度上下限、文件格式限制都写在字段 `description` 文案里**，zod / TS 根本校验不到。
2. 换型验收清单只有「形态校验 + describe 对账」，没有「**实际 payload ↔ 上游真实要求**」这一步；而本批用户明确要求「不实测」，于是唯一的真实反馈被拿掉，缺口无人兜住。
3. 选型阶段是**按功能描述挑模型**（"Full-length songs up to 4 mins"），没有逐字段读 input schema 的 description（600 字上限恰好会卡住"整首歌歌词"这个主场景）。
4. 文件类参数的上游格式限制没有映射到 catalog `ParamSchema.accept`，前端上传槽自然收得过宽。

### 解决方案 / 规则

1. **「不实测」只豁免真实生成，不豁免静态对账**。换型批固定加一步 **fetch-stub 静态复现**：stub 掉 `fetch`，驱动 handler 用典型客户端 body 生成真实 payload，逐档与上游 `latest_version` schema 的 required + **description 里的限制**比对（本批 19 档即由此定位 4 处风险）。
2. **「schema optional 但业务必填」的字段必须显式处置**：要么补齐参数（如参考音频上传槽），要么**下线该档**（本批 `music-01` 走 `deprecated:true` + `deprecated_alternatives`，不删目录、KV 留 ≥30 天）。
3. **硬限在共享工厂兜底**：`createReplicateAudioHandler` 增加通用 `validateInput` 钩子，返回字符串即 `400 INVALID_INPUT`（文案带字段名/上限/当前值），**不提交上游、不计费**；共享层只留通用逻辑、零模型知识（守卫脚本扫描仍然干净）。
4. **文件格式限制进契约**：catalog `file` 参数用 `accept` 表达上游真实格式，前端上传槽读 `accept` 校验，不要各写一套白名单。
5. 选型时逐字段读 schema description；`description` 里出现 "Valid input: 10-600 characters" 这类句子就是硬契约，要同步进产品文案/守卫。

### 影响范围

- audio-workers：19 档换型批（1 档下线 → singing 6→5 档、4 处风险加固）；`validateInput` 钩子对后续所有 Replicate 音频档生效。
- 同类风险适用于 image / video / 3D / compliance 所有 Replicate（或任何第三方）换型档：**只要验收依赖"描述"而不是"实测"，就有这个缺口**。
- 前端连带：worker 4xx 文案必须能透传到 UI（本批修复了 `INVALID_INPUT` 被吞成 `Generation failed to start` 的问题）。

### 关键学习

1. **schema 通过 ≠ 能跑通**：`required` 是类型契约，`description` 才是业务契约；CI 只能校验我们自己声明的字段，校验不到上游的隐含要求。
2. **「不实测」是一种风险转移**，必须用别的机械手段（fetch-stub 对账）把风险接住，否则它一定会以「用户第一个发现」的形式回来。
3. 选型阶段读描述会漏，"Full-length songs" 与「lyrics ≤600 字」可以同时在同一个模型页上成立 —— 逐字段读，不要读摘要。
4. 结构性不可用的档**不要靠"少传参数"糊过去**：上游宽松 schema 会放行，失败发生在计费之后，止损成本更高。

## 9. 规格转述失真 + fetch-stub 复述错误规格：klein 档 resolution 大小写致线上 400（2026-11-14）

**发现时间**：2026-11-14 15:10（用户线上实测发现）
**涉及范围**：image-workers `ai-text-to-image-flux-3-image-klein`（OpenRouter 新 vendor 首档）；Lead→backend 的任务简报流程；fetch-stub 静态对账方法
**严重程度**：中（该档上线即 100% 失败；无计费损失——上游 all-or-nothing，failed 终态与退款链路正常）
**定位**：image-workers `a28fb31`（引入）→ `e9c78f7`（修复）

### 现象

1. klein 档上线后用户实测必失败，queue consumer 报上游 400 `ZodError`：`resolution` 非法，合法枚举为 `"512","768","1K","1.5K","2K","4K"`（**大写 K**）。
2. handler 里 `RESOLUTION_MAP` 把客户端 `2K` 翻译成 `2k` 发出——恰好把合法值翻成非法值。
3. 上线前的 fetch-stub 静态对账测试**全绿**：它断言的正是 `resolution:"2k"`。

### 根因

1. **Lead 简报数据失真**：OpenRouter endpoints API 的 `resolution` 请求枚举本是大写 `1K/1.5K/2K/4K`（仅 pricing 的 `variant` 标签是小写），Lead 核实时读到了两套大小写，却把旧档 **Replicate** 的小写约定误套到 OpenRouter，简报写成「上游小写」——backend 按错误规格正确实现。
2. **stub 复述了规格而非验证契约**：fetch-stub 对账的断言值来自简报（口头规格），不是来自实拉的上游 schema。stub 测试只能验证「实现与规格说明一致」，规格说明本身错时它必然绿——对账失去意义。
3. 机械校验（typecheck/registry/guard）与 CI 全绿，同样校验不到「发出的值上游认不认」。

### 解决方案 / 规则

1. **简报数据必须溯源到实拉 API 原文**：凡给 teammate 的参数枚举/字段名/计价数字，附「实拉来源 + 日期 + 原始 JSON 关键段」，禁止凭记忆/类比其它 vendor 转述；两套口径并存时（本例枚举大写 vs pricing variant 小写）显式写明各自用途。
2. **fetch-stub 断言的数据源 = 实拉上游 schema**：把上游枚举/required 固化为测试内的常量并注明实拉日期，断言 payload 命中该常量；禁止把「简报里写的值」直接写进断言。
3. 大小写类分裂（同一 API 内枚举与标签大小写不一致）是高危形态：上线后首个 4xx 若为 `invalid_value`，优先 diff 实发值与错误体里回显的合法枚举。

### 影响范围

- 仅 klein 档 resolution 参数；aspect_ratio / prompt / input_references 不受影响；catalog / KV / arui 零变更（客户端值与 creditCost key 本就是大写）。
- 该教训适用于所有后续新 vendor 接入与 fetch-stub 对账测试。

### 关键学习

1. **转述即失真**：多 Agent 协作里「Lead 核实过的数据」仍要在简报里附原始证据链，下游无法分辨转述与原文。
2. **stub 对账校验的是「实现 ↔ 规格」，不是「实现 ↔ 上游」**：规格载体（简报/文档）错了，对账就变成错误的放大器而非防线。
3. 新 vendor 的字段命名惯例不能从旧 vendor 类比——哪怕同是「flux-3 image」。

1. **流程闸门补齐后要回收旧保护**：某条保守窗口的存在理由被新闸门（CI verify + TTL）完全覆盖时，它就从「保护」变成「摩擦」，规则要跟着流程演进，而不是等用户第 N 次重复豁免。

## 11. 输出分辨率失真标示：比例驱动尺寸的档被 maxDimension 徽标统一标成 "2K"（2026-11-15）

**发现时间**：2026-11-15（flux-2-max 换 OpenRouter 后的显示口径核查，用户指出）
**涉及范围**：image-workers `ai-text-to-image-flux-2-max-or`（maxDimension / creditCost）；arui `model-list.tsx` 分辨率徽标、`param-form.tsx` 比例选项；所有「上游无 resolution 参数、输出尺寸由比例决定」的档
**严重程度**：中（用户可见的失真标示 + 定价偏差：1:1 实际 1024×1024=1K/成本 $0.07，却被标 "2K" 并统一收 34 积分，多收 ~62%；无资损方向是偏贵，但属信任问题）
**定位**：image-workers `cedd60c`（引入 flat 34 + md 2088）→ 本批修复（per-ratio 分表 + md 2400 + 选项标注尺寸 + arui 徽标规则）；arui `60ebd4bcb`（快照）

### 现象

1. OpenRouter flux.2-max 无 resolution 参数，输出像素由比例决定（短边 ~1024）。换型时按「最贵比例保守定价」收 flat 34 积分，且 maxDimension=2088 使 arui 模型卡徽标显示 "2K"（>=2048 即 2K）。
2. 实测证据（OpenRouter 官方计费博客 + 模型页 playground）：1:1 实际输出 **1024×1024（1K）**、实收 $0.07（21 积分）；16:9 = 1824×1024；仅 21:9 达 2400×1024（2.46MP）。即**大多数比例根本不是 2K**，徽标与一口价都失真。
3. 比例选项旁无任何输出尺寸信息，用户选 9:16 与 1:1 拿到的像素数不同却无从得知。

### 根因

1. **上游换源后参数语义降级未连带重审显示层**：resolution 从「用户可选实参数」（Replicate 档 1K/1.5K/2K → 上游 1/2/4 MP，积分挂 resolution 正交严谨）变成「比例的函数」，但 maxDimension 徽标与定价形态（一口价）沿用了旧的「档级」口径。
2. maxDimension 用「总 MP 等面积外推长边」（2.4MP → 2088）推导，而上游真实规律是**短边固定 1024、长边按比例拉长**——外推方法错误，21:9 实际长边 2400。
3. 「保守定价」拍板时没有对照页面 $0.07 的观感差异：页面价是 1:1 的价，我们收的是 21:9 的价，用户一眼看出「贵很多」。

### 解决方案 / 规则

1. **分辨率如实显示：1K 就是 1K，未到 2K 不得标 2K**。档级 md→"1K/2K/4K" 徽标**只在该档 catalog.params 里存在 resolution 参数时显示**（分辨率可选才谈得上档级徽标）；无 resolution 参数的档，输出尺寸在每个比例选项 label 上直书（如 `1:1 · 1024×1024`），实测档直书、推定档加 `≈` 前缀，首批真实账单后回填校准。
2. **计价跟着决定像素数的那个参数走**：比例驱动尺寸的档用 `perUnit(paramRef: aspect_ratio)` 分表（21/25/27/29/34），每个比例贴着自己的真实 MP 定价；禁止再对这类档用「按最贵比例一口价」除非用户显式拍板。
3. **尺寸/计价数字必须有实测锚点再上 UI**：OpenRouter 官方计费博客（真实生成数据）+ 模型页 playground 是两个免实测的锚点来源；纯外推值一律标 `≈` 并注明推定方法。
4. maxDimension 推导注明方法：短边固定型上游按「短边×最大长边」取，不按等面积外推。

> **2026-11-15 补记（口径修订）**：本条初稿（09:21）按「不显示档级徽标 + 比例选项直书尺寸」落规则；同日上午用户 P3 拍板（arui 10:07 起实施，晚于本文）改为**「归档档级动态跟随」**：无 resolution 参数的档经 arui `config/aspect-resolution-archive.ts` 白名单（精确枚举 + 后缀）命中后，按当前比例的长边查共享归档表（<1536→1K / 1536–2047→1.5K / ≥2048→2K）动态出徽标，「直书尺寸」方案作废，不双口径并存。归档表的尺寸数据源仍须实拉证据链——2026-11-15 gpt-image-2.6-flare 接入时以 fal/OpenAI 官方几何锚点证实 gpt 系归档分布与 flux 共享表一致后才复用；新族未经证实不得套表（与本条原规则 3 同源）。规则 2/4（perUnit(aspect_ratio) 分表计价、maxDimension 短边×最大长边）不变。

### 影响范围

- flux-2-max-or 档：积分 21–34 按比例、md 2400、比例选项带尺寸标注；arui 徽标规则改为通用规则（无 resolution 参数即不显示档级徽标）。
- 后续所有「无 resolution 参数」的换型档（OpenRouter Image API 族）默认套用本条规则。

### 关键学习

1. **参数语义变了，展示与计价形态要跟着重审**：「分辨率可选」变「分辨率由比例决定」时，档级徽标、一口价、maxDimension 三个口径都要重新推导，不能只改 handler 白名单。
2. 定价拍板要对照「用户在页面上看得到的价格锚点」（$0.07 是 1:1 的价），保守加价超过锚点 50% 时应主动提示价差而不是默默执行。

## 13. wrangler kv key delete 无 --force：静默失败与 404 文案误判（2026-11-15）

**发现时间**：2026-11-15 19:30–19:35（T2-B2 c 段清理 14 个孤儿 key 时）
**涉及范围**：image-workers 孤儿 KV key 清理（#10 弃用即清理的标准步骤）；所有 worker 仓后续弃用批的 wrangler 清理操作
**严重程度**：低（无资损；操作层坑——不识破会「以为删了」或「以为没删成」反复重试）
**定位**：本仓 wrangler 3.x；T2 批 14 个 model:image:ai-text-to-image-* key 清理

### 现象

1. 批量删除循环首轮**静默失败**：`npx wrangler kv key delete` 在 wrangler 3.x 无 `--force` flag，交互式确认提示在循环里拿不到输入，错误输出被吞——循环跑完像成功，key 全在。
2. 复验时一轮误报 STILL_PRESENT：`wrangler kv key get` 对已删 key 返回 404 时，**报错文案（~480B）打到 stdout**，按「有输出=有值」判定时把 404 文案当成 entry 值。

### 根因

1. wrangler 3.x 的 delete 默认交互确认，无新版 `--force`；脚本循环里 stdin 缺失导致失败但不显式报错。
2. wrangler 的错误/404 输出走 stdout 而非 stderr，与正常 JSON 值同流，简单判空/判存在会误判。

### 解决方案 / 规则

1. 删除用 **stdin 管道确认**（如 `echo y | npx wrangler kv key delete ...`）或逐 key 显式单删。
2. 清理规程固化三态判定：**404 / 空 / JSON 值** 三态区分（404=已删，JSON=仍在，空=异常），禁止用「stdout 有无内容」判断存在性。
3. 批量清理前后各做一次 summary 对账（deleted_ok / still_present 计数），对账口径用三态判定。

### 影响范围

- 本批 14 key 全部按规程删净（deleted_ok=14 / still_present=0，终验全部 404）。
- 后续所有弃用批的 KV 清理步骤直接套用本条规程。

### 关键学习

1. CLI 工具的确认交互与输出流（stdout vs stderr）是脚本化的两个隐形坑，批量操作前先单 key 试跑一次看清行为。
2. 「验证删除」与「执行删除」同样重要：没有三态判定的复验等于没验。

4. **删档/切换批的引用点 checklist 固化五项**：映射 / defaultModelId / remap 表 / 僵尸阈值表 / 归档白名单——批B 起 defaultModelId 已有 CI 门禁兜底（断链即红），其余靠 checklist。
5. **「保留不动」必须显式对照删除清单**：拍保留时同步在删除清单标注排除（如 sankey/venn 的 flux-schnell 两档），两侧白纸黑字。
6. **大范围替换前先盘点 diff 现状 vs 目标**：重做指令先花 10 分钟盘点（批D 盘点报告避免了 159 档无效重生成的全额浪费）。
7. **中间态 CI 红是门禁在正常工作**（本批 5 次红全部是「push→拦截→修复→绿」循环，零带病上线）——红线本身不是事故，**没红线才危险**；但同一根因的红不应重复出现（同源断言两轮红就是教训）。

### 影响范围

- 本批全量换源（127 工具池）按规则执行后零线上影响；规则沉淀进任务书模板与 CI（defaultModelId 门禁）。
- 后续所有批量换源/删档批次直接套用本条 checklist。

### 关键学习

1. **验证工具的错误会放大被验证对象的错误**：断言器与生成器必须异构（不同数据源、不同推导路径），否则对账变成错误的自我确认。
2. **切换型变更的引用面是图不是点**：删除一个档，五类引用点同时受影响——checklist 化是唯一可靠手段。
3. **「不动」是决策，「不被波及」是事实**——两者必须分别确认，删除清单是波及面的唯一真源。
4. 仪式性重做比不做更糟：先盘点，让指令的目标（统一规格）与现状对账后再动手。
5. 基础设施小坑（换行）踩一次是意外、踩三次是流程缺失——第二次踩就该固化输出标准。

## 16. OR「零可用」误判：未过滤主目录当全集 + 模态 token 没枚举全，漏掉专用端点里的 28 视频 / 36 语音候选（2026-11-17）

**发现时间**：2026-11-17 23:0x（用户拿网页 `?output_modalities=video` 实测对质，Lead 三组 curl 复核实锤）
**涉及范围**：§18.5 全站盘点（task-49/50）的「audio/video OR 零可用 → 维持 Replicate」结论；后续 audio-workers / video-workers 换源路线
**严重程度**：高（决策级方向错误；因「先检查不执行」原则未造成实际损失）
**定位**：18档清单 §18.5 vs 本条实拉（curl 三组：未过滤主目录 / 过滤参数+专用端点 / 逐模型 endpoints）

### 现象

1. §18.5 用**未过滤**的 `GET /api/v1/models`（470 项）扫 `output_modalities`：视频输出=2（google/gemini-omni×2）、音频输出=4（google/lyria×2 + openai/gpt-audio×2）→ 排除 Google/GPT 系后判「零可用、停止换源」。
2. 用户当晚清点网页发现筛 video 明明有模型（ByteDance Seedance 2.5 Flash 等）。Lead 复查实锤：
   - 未过滤主目录确实 470 项且**不含** seedance / speechify-simba / seedream-5.5 / recraft-v4.1-flash-v2 / hy-world 等（7 个网页在售 slug 抽样全 miss）；
   - 同一主目录端点**带过滤参数** `?output_modalities=video` 返回 **33** 个；专用端点 `/api/v1/videos/models` 同为 **33**（wan×6 / seedance×6 / kling×3 / hailuo×3 / BFL flux-video×3 / heygen×2 / runway×2 / grok-imagine×3 / veo×3+gemini-omni×2 / tbc×1）；
   - 主目录查 `bytedance/seedance-2.5-flash` **404**，但 `/api/v1/models/{slug}/endpoints` 返回 200 且带完整模态 `text+image+audio+video→video`（speechify/simba-3.5 同理，`text→speech`）；
   - **speech 是独立模态 token**：`?output_modalities=speech` = **39** 个 TTS/语音模型（elevenlabs×9 / fish-audio×4 / microsoft-mai×4 / heygen×3 / minimax×2 / qwen-audio×2 / deepgram×2 / mistral×2 / speechify / grok-voice-tts 等）；只查 `audio`（=4，音乐生成类）会漏掉全部 TTS。
3. 排除 Google/GPT 后真实候选：视频 **28**、语音 **36**——且 wan / seedance / kling / hailuo 与 Replicate 现役池**同家族**，video 换源可行性直接翻盘。
4. 3D 复核维持原结论：模态枚举校验（Zod 报错原文）合法值仅 `text, image, embeddings, audio, video, rerank, decisions, speech, transcription, all`——**无 3d/mesh 类目**，OR 无 3D 输出。

### 根因

1. 把「未过滤主目录」当全集——它对非 Chat 通路（视频/语音/图像专用 API）收录不全（机制未查明，勿断言），只能当下界；
2. 模态 token 没枚举全：speech ≠ audio，TTS 全在 speech token 下；
3. 「主目录 404 = 模型不存在」的错误等价：endpoints API 才是逐模型兜底真源；
4. 违反自家双源交叉原则：图像侧调查（§〇）明写「专用端点 + 全量列表交叉核对」，§18.5 只做了单源（未过滤全量）——#15 关键学习 1 的镜像：数据源同构导致结论自我确认。

### 解决方案 / 规则（「OR 上没有 X」类结论的三源交叉铁律）

1. **专用端点优先**：`/api/v1/images/models`、`/api/v1/videos/models`（语音无专用端点，必走过滤参数）；
2. **过滤参数枚举全部相关 token**：`?output_modalities=video / speech / audio / image` 逐一查（audio 只覆盖音乐生成类，TTS 在 speech）；
3. **逐模型 `/endpoints` 兜底**：网页在售但主目录 404 的 slug 以 endpoints API 为准（404 ≠ 不存在）；
4. **未过滤主目录只能当「下界」**，禁止单独据此出「零可用 / 停止」结论；
5. 模态类目以 Zod 校验合法值清单为准（上列 10 个），判「无某类输出」前先确认该类目存在。

### 影响范围

- §18.5 的「audio/video 零可用 → 停止」**作废**，两域换源评估重开（3D 维持）；28+36 个非 Google/GPT 候选待 backend-audio / backend-video 按 #47 式逐档核查（参数/计费/区域可用性）后再定；
- 2026-11-17 产出的 32 页「未切换 OR」网址清单**不受影响**（页面现状仍 Replicate 是仓内事实；变的是「能不能换」的答案）；
- 本仓所有后续「OR 可用性」调查必须套用三源交叉铁律。

### 关键学习

1. **「零结果」类结论对数据源的完整性最敏感**：查到 2 个和存在 33 个之间，隔的只是一个查询参数；负向结论（「没有」）必须比正向结论（「有」）用更强的多源证据。
2. 上游目录的分表（主目录 / 专用端点 / 逐模型端点 / 网页筛选器）天然不同步，**网页 UI 是免费的第二真源**——用户肉眼看得到的，API 调查漏了，说明调查口径有洞。
3. 枚举类字段（模态 token）先拿全合法值清单再下结论：speech/audio 一字之差 = 39 个模型漏检。
4. 调查方法论和结果一样要过审：§18.5 的「OR 实证」四个字掩盖了「只查了一个端点」的空心。
